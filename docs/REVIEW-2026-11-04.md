# Six-persona project improvement review

Reviewed 2026-11-04 against commit `c18280e`. This is a snapshot of a
work-in-progress application and a planning review, not a certification. The
[backlog](../TASK.md) owns prioritization and acceptance criteria; this document
records why the tasks exist and what was actually observed.

The product goal is an installable, Mandarin-first knowledge podcast studio
where a creator can write, generate, audition, save and export narration. The
owner requires a static GitHub Pages app and **pure browser BYOK without a
required server**. Demo tones are synthetic and not spoken OpenAI samples.

## Evidence and limits

- The owner reported that browser BYOK can now produce WAV files, and that the
  same narrator's delivery, emotion and pauses differ across clips. The reviewers
  did not receive or listen to those WAVs, inspect the owner's key or account, or
  independently verify a live provider response.
- Three independent reviewer agents each examined two different personas:
  product owner and podcast producer; audio engineer and PWA/mobile engineer;
  browser security engineer and QA/reliability engineer. Their reviews were
  consolidated against the repository by the lead agent.
- **Reproduced in a free browser session:** after producing a demo segment,
  pressing its generate button again reported that no segment needed generation.
  All OpenAI requests were intercepted. See `src/App.tsx` `generate` and the
  segment actions.
- **Reproduced with injected storage failure:** a free demo batch continued
  through all five segments after IndexedDB `put` threw a quota error; the UI
  also showed a save failure. The paid path shares the same loop, but no paid
  request was made. See `src/App.tsx` `commit` and `generate`.
- **Reproduced under a controlled timing assumption:** a browser audio graph
  produced two synthetic bursts, with the second delayed beyond the quiet-tail
  timeout after a simulated provider stop event. The result was labeled generated
  while the saved WAV contained only the first burst. The one-off injection was
  not retained as a regression test. This does not prove that the owner's audio
  was truncated or that the real service emitted this event sequence.
- Existing CI uses Chromium; local real WebRTC loopback tests use two browser
  peers and mocked provider events, not OpenAI-generated audio. Earlier live
  single-tab update checks preserved a local draft. Firefox, real iOS and Android,
  multi-tab update, and real-provider speech quality remain unverified.
- A read-only request to the public Pages site found no CSP, `X-Content-Type-Options`,
  `Referrer-Policy` or `X-Frame-Options` response headers. This is a defense-in-depth
  observation, **not** a finding that an exploitable XSS exists. Pages controls
  available to a static site must be checked before prescribing a header.

## Product owner

**Finding.** Batch validation occurs as each segment is generated, and import
limits differ from provider-side limits (`src/App.tsx`, `src/browser-tts.ts`,
`src/backup.ts`). A later invalid segment can fail after earlier segments have
already been generated. The visible segment action also cannot regenerate
current audio, and audio is excluded from the only backup format.

**Recommendation.** Preflight the entire run; add explicit re-record with a
cost notice and retain the old take until the new one is safely saved. Add an
optional audio-inclusive backup without removing the existing script backup.
See T01, T03, T04 and T09.

## Podcast producer

**Finding.** The owner's issue concerns continuity of the *same* voice, not
necessarily a voice-selection error. Each segment is generated as a separate
session with only its own text, and the current documentary instruction is broad
(`src/App.tsx`, `src/browser-tts.ts`, `src/model.ts`). Independent phrasing and
segment boundaries are plausible contributors, not a proven diagnosis of the
owner's WAVs.

**Recommendation.** Compare a short continuous response, multiple responses in
one session, and segmented generation with limited context. Define a human
listening rubric for pacing, emotional consistency, boundaries and exact wording.
Compare cost, timeout and recovery before choosing; no approach guarantees
identical prosody. See T05–T08.

## Audio engineer

**Finding.** Capture ends using an audible-signal and quiet-tail heuristic;
`pcmToWav` preserves up to 150 ms before and 250 ms after detected sound, while
`joinDemoWavs` directly concatenates compatible mono PCM data. The result has no
configurable transitions or loudness matching (`src/browser-tts.ts`,
`src/audio.ts`). A heuristic cannot prove that no late media is forthcoming.

**Recommendation.** First prevent incomplete audio from being represented as
confirmed complete. Then add a non-destructive boundary preview and optional
pause, fade and loudness treatment, with tests that protect quiet syllables and
do not overlap words. Assess sound quality by listening, not waveform tests alone.
See T02, T07 and T08.

## PWA and mobile engineer

**Finding.** Single-tab update checks exist, but activation claims clients and
removes prior caches while the guard checks the initiating tab
(`scripts/build-sw.mjs`, `src/App.tsx`). A second tab might still be editing or
generating; this is a source-based risk, not a reproduced incident. Keyless demo
generation is also disabled when offline, as current tests explicitly expect.
Real mobile behavior of repeated audio context startup is not verified.

**Recommendation.** Specify cross-tab update coordination and old-resource
retention; test editing, running work and offline recovery in two tabs. Make an
explicit product decision about offline demo generation, and verify mobile
autoplay and multi-segment behavior on real devices. See T12, T14 and T15.

## Browser BYOK security engineer

**Finding.** The project explicitly accepts the risks of a user-entered standard
key in the page runtime. Application code clears it in normal lifecycle paths
and does not intentionally persist it, but scripts, extensions, password tools
or a compromised deployment can access or retain sensitive values. The review
found no proof of key theft or a specific injection vulnerability.

**Recommendation.** Keep consent and cost warnings; evaluate CSP as defense in
depth and test the actual static deployment without breaking required media and
PWA features. Scope workflow permissions and pin verified action versions.
Describe remaining limitations; a CSP cannot make browser BYOK equivalent to a
trusted backend. See T10.

## QA and reliability engineer

**Finding.** Automated tests cover simulated generation, persistence, offline
shell, user-approved PWA update and Chromium loopback. They do not establish
provider speech fidelity or cross-device behavior. `session.created` is used
as a readiness signal without verifying an effective voice/model, and recorded
voice metadata is the requested value; whether the provider exposes a suitable
confirmation needs current documentation. The media element's asynchronous
`play()` rejection is tested for an immediate rejection, not all late races.

**Recommendation.** Add reproducible quota, delayed-tail, playback-rejection,
connection/cancel and multi-tab fault injection. Separate mocked tests from
real-track tests, owner-reported live success and optional paid evaluation.
Explicitly mark unsupported or untested outcomes. See T01–T03, T11, T12 and T15.

## Decision boundaries

- Keep all existing API-key warnings and session-only behavior; no backend or
  persistent credential store is a prerequisite for this roadmap.
- A future continuity experiment may send additional neighboring script text to
  the provider; describe the data scope and cost before any authorized trial.
- A stronger prompt, shared session, one long response or audio smoothing may
  improve continuity; none has been demonstrated to fix the owner's exact sample.
- Never turn estimated prices, hypothetical rainfall comparisons, mocked speech
  or browser loopback into claims of verified billing, measurements or natural
  narration.
